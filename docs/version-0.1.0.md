# v0.1.0：旅行 ReAct Agent 框架化阶段记录

记录日期：2026-10-23。源码基线：`d8ba535`，本文描述该基线读取到的实现，不包含本文之后的功能变更。版本名是阶段编号，不表示已经建立 Git 标签或发布 Release。

## 这一阶段解决了什么

起点是 main.py 中直接执行的旅行 ReAct 脚本。现在将模型通信、决策循环、工具执行、历史和配置拆成独立模块，保留“当前天气 → 景点建议”的业务链路。目标是让代码可理解、可复用、方便继续扩展，并未在这一阶段完成商业旅行产品。

## 一次任务如何执行

1. main.py 调用 load_dotenv，加载提示词并注册工具。
2. AgentConfig 读取最大步数；LLMConfig 读取模型、密钥、地址、超时和 temperature。
3. 创建 OpenAICompatibleClient，再把客户端、注册表和提示词传给 ReActAgent。这种从外部传入依赖的方式称为依赖注入。
4. run() 清空上一次消息历史，加入用户问题，用 ToolRegistry.describe() 填充提示词中的 `{tools}`。
5. 每一轮将历史交给模型。客户端将 Message 转成请求字典；内部 tool 消息转换为带 `Observation:` 前缀的 user 消息。
6. Agent 保留一组 Thought / Action 文本并记录模型输出，提取 Action。
7. Finish[...] 格式正确就返回答案；否则尝试解析工具调用。
8. ast.parse 读取调用结构，限制为简单函数名和关键字参数；ast.literal_eval 读取字面量。注册表按名称找到函数，用 signature.bind 检查参数绑定，执行并记录耗时。
9. 工具返回值或解析错误作为 Observation 进入历史，下一轮模型能够读取它。
10. 达到步数上限返回未完成提示；模型请求异常通过 LLMError 传到 main.py，由入口展示失败。

模型生成的是行动文本，Python 才执行工具。Thought 是模型输出的解释性文本，不能用来证明模型内部推理过程或答案正确性。

## 模块职责与关键设计

| 模块 | 负责什么 | 为什么这样拆 |
| --- | --- | --- |
| main.py | 组装与启动 | 明确组件依赖和运行入口 |
| Agent | 抽象 run、消息增删读 | 为执行策略提供公共接口 |
| ReActAgent | 循环、Action 解析、停止条件 | 将决策流程从具体 API 中分离 |
| Message | role 和 content | 内部历史有结构，便于转换 |
| OpenAICompatibleClient | 消息适配、SDK 请求、LLMError | Agent 不需要直接操作 SDK |
| AgentConfig / LLMConfig | 执行参数 / 模型连接参数 | 配置按职责划分，无需单例 |
| ToolRegistry | 注册、描述、参数绑定、执行和记录 | Agent 使用统一 execute 入口 |
| BaseTool / WeatherTool | 类形式工具接口与天气包装 | 复用现有函数，并支持工具对象注册 |

WeatherTool.run(city) 转调用 get_weather(city)。register_tool() 注册的是绑定方法 tool.run，后续仍复用函数执行路径。景点工具直接注册函数，两种形式可以共存。

## 已实现能力的准确边界

- **消息历史不是长期记忆**：每次 run() 清空历史，只保存本次任务；没有持久化、跨轮对话和上下文裁剪。
- **是文本 ReAct**：没有实现原生 function calling。原生 tool 消息需要 tool_call_id 和对应 tool_calls，当前客户端因此把内部 tool 消息适配为 user Observation。
- **参数检查是绑定检查**：signature.bind 检查缺失、多余和错误名称，不验证值是否符合 str/int 等类型，也不验证城市是否有效。ToolParameter 目前主要用于描述，不参与类型校验。
- **类型标注不等于运行时校验**：Message 使用 dataclass；Literal 主要帮助静态检查，不能阻止运行时传入任意角色。frozen 配置禁止字段重赋值，但不是全面数据校验系统。
- **工具描述有限**：describe 展示名称、类型和工具用途，尚未展示参数 description、required 和 default。用户已决定暂不增加这项展示。
- **解析受限而非完整沙箱**：没有 eval，也不执行模型表达式；只允许已注册函数和字面量参数。不过没有输入长度、嵌套深度限制，重复关键字可能被字典覆盖，仍需后续完善。
- **success 不等于业务成功**：工具自己捕获网络错误并返回字符串时，注册表仍记录 success=True。当前 success 只表示签名检查和函数执行未抛出异常。
- **日志是内存记录**：无持久化、请求 ID 和任务隔离。Agent 清空历史不会自动清空注册表日志，多次 run 时记录可能累积。
- **副本是浅副本**：get_history 和 get_execution_records 复制列表，列表中的对象仍共享，外部仍可能修改对象字段。
- **超时不是任务总截止时间**：天气请求连接/读取超时为 5/10 秒；Tavily search timeout 为 10 秒。模型 timeout 来自配置，SDK 重试可能增加总耗时。
- **多 provider 是配置预设**：按显式 LLM_PROVIDER 选择默认地址和密钥名，没有自动推断 provider，也未验证所有平台。OPENAI_BASE_URL 会覆盖默认地址。
- **配置校验有边界**：有 provider、步数、timeout 和 temperature 范围检查；模型与密钥是否为空、服务商模型是否有效等尚未完整验证。

## 实际排错经验

1. Message 无法 JSON 序列化：Agent 改传消息对象后，客户端还在旧接口。修复是统一接口并在请求边界转换字典。
2. 工具消息协议：内部 role 不应不经适配直接当作 API tool 消息发送；当前文本协议通过 user Observation 传结果。
3. process() takes no keyword arguments：完整 traceback 指向 httpx2 解压代码，而非 Action 解析。环境采用 openai 1.x 与 httpx 0.27/0.28 范围恢复运行。注意当前 requirements.txt 仍未保存该约束。
4. 调用失败被当成回答：原先返回错误字符串导致 Agent 不断找 Action。现在用 LLMError 中止任务，区别于可反馈给模型的格式错误。
5. WeatherTool 导入失败：仅修改 main.py 的导入不够，还要定义并保存工具类、基类和注册方法。
6. observation 未赋值、kwargs 拼写错误：先核对磁盘文件与控制流，再检查缩进和变量名。编辑器未保存会造成修改与运行不一致。

## 面试复习：用自己的话回答

**30 秒介绍**：我把一个查询天气并推荐景点的 Python ReAct 脚本改造成模块化 Agent。模型负责选择行动，程序解析受限 Action，通过工具注册表执行查询，并把结果回传模型。实现了公共 Agent 接口、消息结构、配置分离、异常和执行记录。当前是单任务原型，没有长期记忆和量化效果指标。

**为什么不是固定串联两个工具？** 当前工具选择和结束时机由模型结合 Observation 决定。灵活性更高，但格式依从、工具误选和额外模型调用是代价。固定业务流程也可以用普通工作流实现。

**为什么不用 eval？** 模型文本不能直接作为可执行代码。AST 只识别调用形状，literal_eval 只读取字面量；最终函数来自注册表白名单。

**如何避免无限循环？** 最大步数限制，每轮通常一次模型请求；Finish 提前结束，LLMError 使任务中止。步数限制没有覆盖工具阻塞，所以还要网络超时。

**Memory 和 history 有什么区别？** 当前 history 是本次任务上下文；长期记忆还需要明确保存范围、检索方式、更新和隔离策略，尚未实现。

**工具校验可靠吗？** 当前只能检查调用形状和参数绑定，不能保证类型和业务含义正确。不能把 signature.bind 称作完整 Schema 校验。

**框架化带来什么收益？** 模型适配、工具执行和 Agent 策略职责分开，替换组件更方便。没有基准测试，不能声称成功率提高多少或性能提高多少。

**如果上线还缺什么？** 可复现依赖、自动化与端到端评估、结构化工具结果、来源可追溯、会话隔离和持久化、输入约束、运行预算及可用性策略。具体顺序待产品目标明确后确定。
